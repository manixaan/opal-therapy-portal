## 7. Technical detail

### Why the tracker already had detailed notes before tonight ran

Before any verification tonight, the fetched tracker snapshot already carried fully-written `claude_update` and `next_action` text for every one of the 13 features, with the same level of technical specificity this audit produces (e.g. a precise claim about `/api/outlook/categories` returning an untested 500 for a disconnected user). This audit's own checkout of `develop` only has `README.md` under `docs/qa/nightly/`, which initially looked like a first run.

It is not: `claude/nightly-audit` already carries three prior briefs (`2026-10-15.md`, `2026-10-16.md`, `2026-10-17.md`, plus `LATEST.md`) and an open, unmerged PR (#1, opened 2026-09-17). Each night's audit writes back to the tracker *before* pushing (by design, so a push problem never costs the tracker its update), then pushes to `claude/nightly-audit` and updates the same PR — which is never merged into `develop`, so `develop` itself never accumulates these docs. Tonight's run fetched `origin/claude/nightly-audit` once this was discovered and merged it in before committing, rather than overwriting that history with `--force-with-lease` as the bootstrap's literal Deliver steps would otherwise have done.

This audit still treated the pre-existing `claude_update`/`next_action` text as **prior findings to independently re-verify, not ground truth**, and re-derived every conclusion in this brief from the actual code, tests and QA docs before writing anything. The two sets of findings mostly agree (expected, since nothing in Xero/FCA/Assessments/Resource-Hub/Mobile/Inductions/Profile/Reminders changed in the window — see §6), which is exactly what should happen when a tracker's cards are honestly in sync.
